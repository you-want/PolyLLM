# PolyLLM v0.5.0 规划：能力补齐与推广就绪

> 状态：建议方案，尚未开始实现；2026-10-23 建立。
> 基线：v0.4.0 已完成 npm / PyPI 发布（2026-10-23，tag `v0.4.0`，release commit `585faf0`）。
> 目标：落地 0.4.0 明确延期的 P1 项，消除 0.4.0 发布暴露的运维缺口，补齐推广前的"能看"资产，为公开发布做准备。

## 1. 为什么是这一版

0.4.0 把协议、错误分类、超时/取消/重试和跨语言门禁做完了，属于"稳定协议"版本。但发布过程和 P1 延期记录（[0.4.0 计划 §11](v0.4.0-plan.md)）暴露了三类未解决问题：

| 现状与证据 | 0.5.0 要补齐的缺口 |
| --- | --- |
| 0.4.0 发布中 `publish-next` 遇 npm 503，6/9 包失败且 changesets 把部分 503 误报进成功列表，只能全量重跑靠 skip 补传 | 发布工具缺标签预检、部分成功清单与有限重试，人工核对成本高 |
| Gemini 两端 `vision=false`，`image_url` 直接抛 `UNSUPPORTED_PARAMETER`（0.4.0 边界，D6） | base64/data URL 图片输入未实现，视觉能力无法对 Gemini 开放 |
| `listModels` 保持插件自身默认超时（D9），不在统一调用预算内 | 模型发现可能无界挂起，与 chat 的超时语义不一致 |
| 官网在线但无"点开即跑"的在线 demo；README 有 Quick Start 但需本地安装 | 推广前缺低门槛的公开演示 |

## 2. 版本范围与边界

**P0：必须完成。**

- T1：npm 发布恢复工具（标签预检 + 部分成功清单 + 暂时性错误有限重试）。
- T2：Gemini base64 图片输入（data URL 映射 + 媒体类型/大小校验，保留 `image_url` 远程 URL 拒绝行为）。
- T3：`listModels` 接入统一超时选项（chat/listModels 共享预算语义）。

**P1：P0 通过后再做。**

- T4：在线 demo 模板（StackBlitz / CodeSandbox，免 clone 体验，预置 Mock 供应商）。
- T5：推广就绪检查（README 顶部 demo 入口、官网示例、GitHub 展示、发布前推广清单）。

本版**不新增供应商、不启动 Rust/Go/Java、不做 1.0 稳定性承诺**。P1 全部延期到后续版本，不降低 P0 标准。

## 3. T1：npm 发布恢复工具（P0）

0.4.0 发布实测暴露：`pnpm changeset publish` 遇 registry 503 时逐包失败，部分包已上传、部分未上传，且失败列表与成功列表可能重叠（503 响应先打 error 再被算进 success）。维护者只能全量重跑，靠"已发布版本自动 skip"补传，但无法预知哪些包真正缺失。

改进 `scripts/promote-npm-dist-tag.mjs` 与 `release-npm.yml`：

- **标签预检**：`publish-next` 前逐包 `npm view <pkg> dist-tags` 与目标版本，输出"已存在/缺失/标签错位"三类清单；缺失才进入上传。
- **部分成功清单**：每次 `changeset publish` 后逐包核对目标版本是否真的在 registry（不能信任 changesets 的成功列表），输出 `已上传 / 未上传 / 标签已移 / 标签未移` 四类状态。
- **有限重试**：对 5xx/503 等暂时性错误做有限次（≤3）指数退避重试；对 403/409 不重试，直接报告并退出非零。
- **幂等可重跑**：已正确设置的标签跳过（`already set` 不算失败）；部分成功后重跑只补缺失项，不重传已传 tarball。

验收：模拟 503 注入（或真实 registry 抖动）后，工具输出能精确指出缺失包；重跑只补缺失；403/409 不循环重试。更新 `docs/release.md` §9 恢复规则，把"全量重跑"改为"按清单补传"。

## 4. T2：Gemini base64 图片输入（P0）

0.4.0 明确 `vision=false`：`image_url` 远程 URL 抛 `UNSUPPORTED_PARAMETER`（TS `wire.ts:83`、Python `plugin.py:226`）。本版开放 base64 路径，不开放远程 URL 自动下载（SSRF 边界保持）。

- **输入映射**：`image_url` 中 `data:` 前缀（`data:image/<mime>;base64,...`）映射为 Gemini `inlineData`（`mimeType` + `data`）；纯 base64 字符串需显式 `mimeType`。
- **校验**：媒体类型白名单（`image/png` / `image/jpeg` / `image/webp` / `image/heic` / `image/heif`）；单张大小上限（建议 20 MiB，对齐 Gemini `inlineData` 限制）；超限或不支持类型抛 `UNSUPPORTED_PARAMETER`，`details.parameter` 指明原因。
- **能力声明**：通过测试的 Gemini 模型在 `specs`/`models` 中翻为 `vision=true`；未验证的继续 `false`，矩阵中注明限制。
- **远程 URL 仍拒绝**：保持 0.4.0 行为，不引入自动下载；矩阵与迁移文档说明。

验收：TS/Python 两端 base64 图片的 wire 构造、媒体类型/大小校验、非法输入报错有测试；0.3/0.4 基础 fixture 不受影响（base64 是新增输入，不改既有 `image_url` 语义）。更新 `docs/compatibility.md` Gemini 行与 `docs/migrations/`（新增 `v0.4-to-v0.5.md`）。

## 5. T3：`listModels` 接入统一超时（P0）

0.4.0 D9 把 `listModels` 排除在统一超时外，保持插件自身默认。本版把它纳入调用预算语义，使模型发现不会无界挂起。

- **公共入口**：`listModels({ timeoutMs })` / `list_models(timeout_ms=...)`，缺省 `undefined`/`None` 表示不做 Core 层预算（transport 仍有 socket 级兜底）。
- **语义**：与 chat 的 `timeoutMs` 同属"调用总预算"，文档说明模型发现是单次请求，无重试/退避参与。
- **插件覆盖**：6 类官方插件（含 OpenAI-compatible）的 `listModels` 接收并应用该选项；动态发现路径同步。

验收：两端 `listModels` 传 `timeoutMs` 在慢响应下按预算中断并分类为 `timeout`；不传时行为与 0.4.0 一致（不回归）。更新 `docs/protocol.md` §6 与 D9 结论，把"暂不接入"改为"已接入"。

## 8. T6：发布（P0 完成后再做）

- 复用 0.4.0 已验证的发布手册流程；T1 的恢复工具在本版发布时首次实战。
- 遵循 [发布手册](../release.md) 完成 next/TestPyPI/正式发布/安装验收/发布记录。
