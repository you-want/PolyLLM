# PolyLLM v0.3.0 规划（生态扩展）

> 状态：已完成并发布（2026-10-16）；本文保留实施前的设计记录，具体交付与限制以 [0.3.0 发布说明](../release/v0.3.0.md) 为准。
> 前置版本：v0.2.0（已发布）
> 定位（roadmap.md）：`0.3.0` 生态版本 —— 增加更多协议插件和自定义插件模板
> 边界（已和之前讨论对齐）：协议稳定性类的能力（统一错误分类、Retry/backoff、跨语言一致性测试、JSON Schema、Tool/Vision/JSON Mode 一致性、插件兼容矩阵）全部归入 `0.4.0`；Rust / Go / Java 暂不启动

## 一、范围（最终版）

| 项 | 形态 | 说明 |
| --- | --- | --- |
| `polyllm-gemini` | 新增 npm + Python 插件包 | 独立 wire（Gemini REST `generateContent`），不走 OpenAI-compatible |
| `polyllm-ollama` | 新增 npm + Python 插件包 | 默认 `http://127.0.0.1:11434`、无 Key 也能跑通（本地探测），wire 复用 openai 的构造/解析函数 |
| OpenRouter / Qwen / Moonshot / Groq / vLLM / LiteLLM | **OpenAI-compatible 预设配置模板** | 不出独立包；在 `@you-want/polyllm-openai-compatible` 内置预设（Base URL + 默认模型清单），Studio/CLI 可直接选中 |
| 自定义插件脚手架 | `polyllm-cli` 新增子命令 `new-plugin` | 生成一个可发布的假供应商包骨架（含 mock 测试样例 + 发布检查清单），与现有 `init` 共用"生成项目文件"的模式 |

## 二、现有代码的关键事实（影响怎么做）

1. **插件代码高度模板化**：`packages/deepseek/src/index.ts`、`packages/openai-compatible/src/index.ts` 结构几乎一致——都直接 import `@you-want/polyllm-openai` 的 wire 构造/解析函数（`buildOpenAIRequestBody`/`parseOpenAIResponse` 等），只是换掉 Base URL、默认模型清单和 `resolveProviderRuntime` 的 provider 名。Gemini 和 Ollama 可以照抄这个骨架，Ollama 几乎可以直接复制 openai-compatible，把默认 Base URL 和"缺 Key 时是否报错"改一下。
2. **预设应该放在 `openai-compatible` 包里而不是 Studio 里**：`packages/studio/src/generators.ts` 的 `providerCatalog` 目前只有 4 个固定供应商，它是 Studio/CLI 生成项目时的"供应商列表"。如果预设做成 `openai-compatible` 包内的一等能力（例如导出 `openaiCompatiblePresets`，每项带 `baseUrl`/`recommendedModels`/`apiKeyEnv`），Studio 只需在"OpenAI 兼容厂商"面板里加一个"预设选择器"下拉框，不需要为每家预设新增一个 `StudioProviderId`——这样 Studio 改动量最小，也避免预设数量以后膨胀时 Studio 类型要跟着改。
3. **CLI 的"生成物"模式已经很成熟**：`packages/cli/src/project.ts` + Studio 的 `generators.ts` 共用一套"生成项目文件树"的能力，`new-plugin` 应该复用这套模式（生成的是"插件包"而不是"用户应用项目"，字段集不同，但输出机制可以照搬）。
4. **Python 侧是完全独立的一套实现**（`python/packages/*`，不是从 TS 生成的），所以 Gemini/Ollama 的 Python 侧要单独写一份对应 wire，工作量不能按"翻译一次就完事"估。
5. **changesets 目前是单仓固定包集合**（`.changeset/config.json` 没有 `linked`/`fixed` 规则，只 ignore 了 `studio-app` 和 `example-typescript`），新增 `gemini`/`ollama` 两个包需要各自单独出 changeset，不需要改现有包的版本号联动（它们是纯新增，不动 core）。

## 三、任务拆分（按可独立合并的 changeset 粒度）

### T1 Gemini 插件（TS + Python）
- `packages/gemini/`：`index.ts`（`geminiPlugin`：`createModelSpec`/`chat`/`chatStream`/`listModels`）、`wire.ts`（`buildGeminiRequestBody`/`parseGeminiResponse`/`parseGeminiStreamEvent`，映射 `candidates`/`promptFeedback`、thinking parts、`finishReason` 到统一协议；不支持的地方按 `ModelSpec.capabilities` 如实声明，比如 `functionCalling: true` 但要先确认 Gemini 的 tool 语义是否完全能塞进 `UnifiedTool`，不行就 `jsonMode: false`/`functionCalling: false` 显式降档，和现在 anthropic 插件处理 `jsonMode` 的方式一致）
- `packages/gemini/src/models.ts`：初始模型清单（`gemini-2.5-flash`/`gemini-2.5-pro` 级别，带别名和快照，格式照抄 `openAIModels`/`anthropicModels`）
- Python 侧 `python/packages/gemini/` 对应实现
- 集成测试：Mock Gemini 的 `generateContent` + `streamGenerateContent`（SSE/流式）+ 4xx 错误
- 不新增 core 字段；如果 Gemini 某个能力现有 `ModelSpec.capabilities` 表达不了，**先停在这里上报，不私改 core**（core 字段变更属于 0.4.0 协议稳定范围，v0.3.0 不动）

### T2 Ollama 插件（TS + Python）
- `packages/ollama/`：几乎照抄 `openai-compatible`，改动点：
  - 默认 `baseUrl = http://127.0.0.1:11434`（Ollama 0.5+ 才默认开 OpenAI 兼容端点；如果要用它自己的 `/api` 协议再单独评估，v0.3.0 先只覆盖 OpenAI-compatible 端点，成本最低）
  - 缺 `apiKey` 不报错（本地服务不需要 Key），改 `resolveProviderRuntime` 的调用方式或传一个空字符串占位——要确认 `resolveProviderRuntime` 是否允许空 key，这是唯一一个可能需要动 core 的小口子，**如果确实需要，作为 0.3.0 唯一的、有明确理由的 core 小改动，而不是顺带做**
  - `listModels` 走 Ollama 的 `/api/tags`（原生接口），而不是 OpenAI 的 `/models`，这是它和 openai-compatible 最大的实际差异点
- Python 侧 `python/packages/ollama/`

### T3 OpenAI-compatible 预设（OpenRouter / Qwen / Moonshot / Groq / vLLM / LiteLLM）
- `packages/openai-compatible/` 新增 `presets.ts`：导出 `openaiCompatiblePresets`，每项 `{ id, name, baseUrl, apiKeyEnv, defaultModels, notes }`
- Studio 的"OpenAI 兼容厂商"面板加一个预设选择器：选中后自动填 Base URL / API Key 环境变量名 / 默认模型，用户仍可以手动改
- CLI `doctor` 对预设的 Base URL 做一次连通性探测（复用现有探测逻辑）
- 文档：`docs/getting-started.md` 补"如何通过 OpenAI-compatible 预设接入 OpenRouter/Qwen/…"

### T4 自定义插件脚手架（`polyllm-cli new-plugin`）
- 生成物：`package.json`、`src/index.ts`（`LLMPlugin` 骨架 + mock 测试样例 + 一个 `README` 说明怎么发布）
- 复用 `packages/cli/src/project.ts` 的"文件生成"机制，新增一个"模板类型"（现在是 `typescript`/`python` 用户项目，现在是"插件包"，字段集不同但输出机制照搬）
- 生成的假供应商包要能通过现有 `pnpm verify:packages`（exports/types/CLI 冒烟那套），这样脚手架本身有质量门禁

### T5 集成与验收
- `packages/integration` 的依赖清单补上 `gemini`/`ollama`（现在只列了 4 个官方插件）
- `pnpm verify:integration` 全绿
- Python 侧对应 `python/run_tests.py` / `verify_packages.py` 全绿
- 预设在 Studio 里的端到端：选预设 → 生成 ZIP → 用生成的项目能跑通（至少 mock 层面）

### T6 发布与文档
- 两份 release note：`docs/release/v0.3.0.md`（TS 侧全部改动）；Python 侧这次**有实质新增功能**（两个新插件包 + 预设逻辑如果也同步到了 Python 侧），所以要补 `docs/release/python-v0.3.0.md`（不再是"版本号同步、功能未变"那种占位）
- `docs/roadmap.md`：勾选 0.3.0 完成项；版本目标表 `0.3.0` 一行补实际交付物；确认 0.4.0 那一节已经把错误分类/Retry/JSON Mode/跨语言测试全部写进去（roadmap 目前第三优先级还有未勾选项，需要在 0.3.0 规划里明确写"这些项推迟到 0.4.0"，避免歧义）
- `docs/api-stability.md` 不新增公共 API 承诺（0.3.0 没有 core 公共 API 变化，除了上面 T2 里那个"Ollama 空 key"的小口子，如果要动 core 需要在里面补一句说明）

## 四、里程碑建议

| 阶段 | 内容 | 退出标准 |
| --- | --- | --- |
| M1 | T3 预设（改动最小，纯文档 + 选择器，先跑通"预设→Studio→生成项目"这条链路） | Studio 里能用预设完成一次完整生成 |
| M2 | T2 Ollama 插件（TS+Python+集成测试） | `pnpm verify:integration` 通过 |
| M3 | T1 Gemini 插件（TS+Python+集成测试） | `pnpm verify:integration` 通过 |
| M4 | T4 `new-plugin` 脚手架 | 用脚手架生成一个假供应商包，过 `pnpm verify:packages` |
| M5 | T5 全量集成验收 | TS+Python 全部门禁绿 |
| M6 | T6 发布 | `pnpm verify:release` 通过 |

## 五、实际交付决策

1. Ollama 聊天使用 OpenAI-compatible `/v1/chat/completions`，模型发现使用原生 `/api/tags`；未新增 `/api/chat` 实现。
2. `new-plugin` 交付 TypeScript 插件模板，Python 插件模板未交付。
3. Gemini 交付工具调用与流式；图片输入明确声明 `vision=false`，JSON Mode 为不支持，没有为了覆盖供应商全部能力扩张 Core。
4. 后续协议工作转入 [0.4.0 计划](v0.4.0-plan.md)，发版统一使用 [发布手册](../release.md)。
