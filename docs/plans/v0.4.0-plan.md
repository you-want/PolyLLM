# PolyLLM v0.4.0 规划：协议与可靠性

> 状态：P0 开发完成（T1–T5 已合入 `release/0.4.0`），T6 发布中；2026-10-16 建立。
> 基线：v0.3.0 已完成 npm / PyPI 发布。本文是 0.4.0 范围与验收依据；T2 错误分类、T3 超时/取消/重试、T4 契约门禁、T5 能力矩阵已实现。
> 目标：同一份业务输入在 TypeScript 与 Python 中获得一致的协议语义、可判断的错误和可控的请求生命周期。

## 1. 为什么先做这一版

0.3.0 已覆盖 Core、6 类供应商插件、OpenAI-compatible 预设、Studio 和 CLI。下一步的主要价值是让用户能可靠处理失败、取消和供应商差异，减少每个项目自行补适配的成本。

代码基线核对：

| 现状与证据 | 0.4.0 要补齐的缺口 |
| --- | --- |
| TS/Python `core` 已有 9 个公共错误码，HTTP 错误多归为 `PROVIDER_ERROR` | 区分认证、限流、服务异常、网络、解析、超时、取消；保留现有错误码兼容性 |
| TS `ChatOptions` 已有 `signal` / `timeoutMs`，多个插件各自合并 AbortSignal | 收敛超时/取消语义，覆盖读取流期间的行为与清理 |
| Python `ChatContext` 有 `timeout_ms`，client 创建 context 时未暴露对应选项；多个插件使用 `asyncio.to_thread` + `urlopen` | 补公开超时入口，明确 task 取消能否停止底层 I/O，不能仅取消等待就声称连接已关闭 |
| TS/Python 类型独立维护；Python 多用 snake_case，流式 `delta` 较宽泛 | 建立语言无关 JSON 契约、明确序列化映射、共享 fixtures |
| Gemini 两端均声明 `vision=false`、`jsonMode=false`；部分动态模型保守声明能力 | 支持范围如实声明；不把供应商理论能力当成当前插件已实现能力 |
| 已有 Mock HTTP、打包安装、生成项目门禁 | 增加双语言契约门禁，覆盖失败、真实流分片和资源释放 |
| 发布依赖多个外部服务，npm 提升脚本逐包执行、首错退出 | 增加发布预检/状态汇总，避免部分成功后的人工猜测 |

## 2. 版本范围与边界

**P0：必须完成。** 错误分类、统一超时/取消、显式可选的重试、Schema 与双语言契约测试、插件兼容性矩阵、迁移指南。

**P1：P0 通过后再做。** 在可清晰表达输入格式的前提下补 Gemini base64 图片输入；加强 npm 标签预检与恢复提示。若影响 P0 交付，单独记录延期，不降低 P0 标准。

本版不新增供应商，不启动 Rust/Go/Java，不引入 Agent/RAG/向量库、自动工具执行、多供应商自动切换，不进行 Studio 大改版。JSON Mode 是 JSON 对象输出语义，不顺带承诺所有供应商支持严格 JSON Schema 输出。

## 3. T1：先写契约与兼容决策（P0）

新增 `docs/protocol.md`：覆盖 request/response/stream chunk、message/content、tool/tool result、usage、finish reason、capabilities、公共错误与生命周期。

- 明确字段必填、缺省、null、空值、未知字段的规则，以及 camelCase ↔ snake_case 映射。
- 统一序列化 JSON 使用 camelCase；Python 用户 API 保留原生 snake_case，不为了 JSON 契约强制重命名现有 API。
- 流式明确文本与工具参数增量的拼接、结束原因、usage 缺失、空增量和异常终止；不把底层网络分片直接当完整事件。
- `AbortSignal`、Python task、API Key、认证 headers 属运行配置，不进入可交换的业务 Schema 或 fixtures。
- 保留微内核边界：Core 定义策略、错误与公共契约；供应商 wire 映射仍归插件，公共执行机制不引入供应商 SDK。

产物：协议文档、TS/Python API 对照表、0.3→0.4 兼容决策清单。后续任务遵循此文档，接口变动同步更新它。

## 4. T2：可判断且不泄漏凭据的错误（P0）

建议保留 `PolyLLMError.code` 及现有 `details`，为供应商错误增加可机器读取的分类与可重试标识。确切字段在 T1 冻结，不提前向用户宣称已实现。

分类至少区分：认证失败、权限不足、限流、无效请求、服务异常、连接异常、无效响应、超时、主动取消。401/403/429/5xx、连接失败、无效 JSON、流中错误必须有确定映射；未知状态保留明确兜底。

- 保留旧 `PROVIDER_ERROR` 判断路径，优先通过新增可选字段表达分类，避免强迫已有调用方重写所有 catch 分支。
- 统一诊断字段语义：provider、HTTP status、request id、retry-after、是否可重试；不要求每个供应商都返回所有字段。
- 不直接复制未经筛选的 headers、URL query 或响应 body 到错误信息；测试故意包含假 key 的错误响应，验证脱敏。
- Python `CancelledError` 与 TS abort 保留各语言可识别的取消机制；对外分类及映射规则在协议文档说明，取消不作为服务失败重试。

验收：6 类官方插件两端均覆盖对应 HTTP/transport 错误映射；既有错误码测试和用户捕获方式保持可用；错误消息与详情不泄漏测试凭据。

## 5. T3：超时、取消与显式重试（P0）

### 先完成 Python transport 可行性验证

用本地慢响应 Mock 验证当前 `to_thread` 路径的取消、读取阻塞与连接释放。T1 阶段据此选择可中止 transport 或资源可控的替代方案；记录依赖、Python 版本支持和插件注入兼容性。不能用“协程已取消”代替底层连接清理的证据。

### 统一生命周期

- TS 保留 `signal` / `timeoutMs`；Python 暴露明确的请求选项，避免超时选项混入业务 payload；支持 asyncio 原生 task 取消。
- 定义 timeout 为整个调用预算，包含尝试、退避和流读取；默认值、无超时表示法、非法数值必须有明确规则，升级带来的默认行为变化写入迁移指南。
- 覆盖发请求前取消、等响应期间取消、读取流期间取消、调用方提前退出迭代、超时与外部取消竞争。
- 取消/超时后释放 reader、连接、timer 等资源；不再后台继续请求或重试。模型发现若暂不接入同一选项，明确其独立超时与支持边界。

### 重试默认关闭

新增可选策略，建议开启时默认最多重试 2 次（总计最多 3 次尝试），指数退避加 jitter，尊重有效 `Retry-After` 并受总时间预算约束。默认关闭可避免升级后调用次数和费用自动增加。

- 仅重试策略明确允许的限流、临时服务或连接错误；认证、权限、无效参数、解析失败和取消不重试。
- 收到首个对用户可见的 stream chunk 后不自动重放，防止文本或工具调用重复。
- 即使未收到响应，供应商也可能已经计费；文档解释重试不保证幂等，Core 不自动执行 tool。
- 不叠加插件或 SDK 内部隐藏重试；统一由一层负责。

验收：注入可控 clock/random 的策略测试验证次数与退避；本地 HTTP 测试验证实际请求次数、总预算及取消后的连接关闭。测试不依赖公共服务或长时间 sleep。

## 6. T4：Schema 与双语言契约门禁（P0）

建议新增：

```text
schemas/                         # JSON Schema 2020-12 与 schema 版本说明
fixtures/protocol/               # 共享合法/非法输入、规范化期望输出
scripts/verify-protocol.mjs      # 拟新增，运行两端 fixture runner 并比较结果
```

协议 Schema 与 SDK 包版本分开说明，不以“0.x”替代契约升级规则。先维护清晰、可评审的 Schema 与两端类型映射，本版不要求全量代码生成。

共享 fixtures 至少覆盖以下场景组，每组包含正常与边界/错误路径：

1. 消息角色、文本与图片部件、system prompt。
2. 普通响应、usage 缺省与 finish reason 映射。
3. 工具声明、多工具调用、分片 arguments、tool result 回传。
4. SSE/NDJSON 分片、CRLF、多行 data、UTF-8 边界、结束与中途失败。
5. JSON Mode、能力拒绝、strict/auto/lenient 参数策略。
6. HTTP/连接/解析错误、超时、取消与重试分类。
7. 模型命名空间、alias、动态模型和缺失能力。

同一 fixture 在 TS 与 Python 运行并比较规范化 JSON；不能两端各维护一套期望来掩盖差异。供应商集成测试另行验证实际 wire 构造/解析，避免只验证类型序列化。

验收：新增 `pnpm verify:protocol`（拟新增命令），接入 CI 与 `verify:stability`；更改任意一端一个公共字段映射会触发失败；合法/非法样例都经过 Schema 校验。既有发布门禁继续通过。

## 7. T5：能力矩阵与迁移文档（P0；Gemini 图片为 P1）

新增 `docs/compatibility.md`：覆盖 OpenAI、DeepSeek、Anthropic、OpenAI-compatible、Gemini、Ollama，逐项列出普通聊天、流、工具、图片、JSON Mode、模型发现、超时、取消和重试。OpenAI-compatible 预设共用 wire，不把通过一个网关 Mock 的结果宣传为全部服务都验证过。

每项区分：已实现且有测试、明确不支持、取决于模型/网关、待真实服务验证。动态模型不能无依据推断能力；本地 Ollama 同样取决于已拉取模型。

- 工具：验证工具定义→模型调用→工具结果回传的完整对话以及流参数拼接，不扩展为自动工具执行。
- 图片：现有协议只有 `image_url`。P1 优先评估 data URL/base64 的明确映射与媒体类型/大小校验；不默认下载远程 URL。若无法保留兼容且通过测试，Gemini 继续声明 `vision=false`，在矩阵中注明限制。
- JSON Mode：支持的模型验证请求映射与输出语义；不支持的模型遵守参数策略并清楚报错，不静默伪装成功。
- 更新 `docs/api-stability.md`、`getting-started.md`、插件脚手架和必要的 Studio 生成配置，提供 `docs/migrations/v0.3-to-v0.4.md`。

验收：矩阵每项支持声明能追溯到测试或明确的外部验证记录；0.3.0 的基础应用/自定义插件 fixture 在 0.4.0 通过兼容测试，无法兼容之处有具体 before/after 示例。

## 8. T6：发布可靠性与正式发布

P1 改进项：npm 提升前确认 9 包目标版本存在、读取当前标签，跳过已正确的标签，失败输出成功/失败/未处理清单并返回非零；权限错误提示 Allow npm dist-tag。只对暂时性错误有限重试，不循环重试 403。

评估 npm workflow 并发保护；明确 PyPI 部分成功恢复与产物复用方案。当前 Python workflow 两次运行分别 build，不能未经验证就宣称按同一产物晋级。若改为复用 artifact，需要覆盖权限、保留时长和版本/commit 校验。

P0 发版验收：9 个 npm 包与 7 个 Python 包版本统一 `0.4.0`，所有旧门禁及协议门禁通过；遵循 [发布手册](../release.md) 完成 next/TestPyPI/正式发布/安装验收/发布记录。规划阶段不提前改版本号。

- **模型发现（`listModels`）接入统一超时选项**：0.5.0 T3 落地（`listProviderModels(provider, { timeoutMs })` / `list_provider_models(provider, timeout_ms=...)`）。
